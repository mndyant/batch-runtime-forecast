# バッチ処理時間・締切超過予測アプリ 初版仕様

作成日：2026-10-03。まず本仕様を固定し、設計レビュー、実装、監査、最終評価、画面確認の順に進める。

## 1. 目的
システム運用担当者が、日によって上下する処理件数と所要時間から、今後のバッチ完了時刻・締切超過・必要な開始時刻を確認する。銀行システム運用の課題を一般化したポートフォリオであり、特定行の内部データ・処理仕様の再現ではない。
「予測値を表示」だけでなく「いつ開始すれば締切と安全余裕を確保できるか」という判断を支援する。

## 2. 初版の範囲
- ローカル、追加の実行費用0円、APIキー・LLM接続不要。
- Python + Flask + NumPy + pandas。HTML/CSS/JavaScriptとローカルSVG。予測、評価、計画、説明、Webルートは分離。
- 1種類のバッチを対象とする。複数ジョブの依存関係、並列スケジューラ、実際の資源増設効果、売買予測は対象外。
- 業務的で簡潔な日本語UI。入力条件と結果を分離し、PC1280px・スマホ390pxで検証。
- サマリ、予測CSV、結果JSONを保存できる。画面・文書で「合成データで評価／実データ未検証」と明記。

## 3. 入力と出力
観測CSVはUTF-8の date,records,runtime_minutes。日次180点を標準とし、毎暦日1行、最低150点・最大3650点、2MB以内。recordsは0以上の整数、runtime_minutesは0以上の有限値。正の処理件数で所要時間0は拒否。処理件数0なら所要時間0または起動処理時間を許容する。
日付重複・欠損日・非数値・負値を拒否し、補間しない。件数や所要時間の減少は有効。
初版のrecordsはその日の確定件数であり、未来の日の件数は未確定として予測する。実際の未来件数を所要時間モデルに渡して精度を良く見せない。

設定：予測期間1/7/30日、予定開始時刻（初期22:00）、締切時刻（初期00:00）、安全余裕15分、比較用の所要時間倍率（初期120%）。
締切時刻が開始時刻以下なら翌日の締切として扱う。このルールをUIに表示する。タイムゾーンは日本時間、暦日計算。営業日カレンダーの祝日判定は初版に含めない。

出力：
- 日別の予測件数、予測所要時間、完了日時、締切日時、締切までの余裕、最終着手日時。
- 状況は「締切超過」「安全余裕不足」「余裕あり」を文字と色で区別。
- 最終着手日時＝締切−予測所要時間−安全余裕。過去日や日跨ぎも省略せず日時表示。
- 締切超過見込み日数、最も余裕が少ない日、サマリ、日別表、実績・予測グラフ。
- 所要時間80/100/指定%の条件比較。確率や統計的予測区間とは表現しない。
- 過去の監査区間で予測と実績を重ねる比較画面。未来の正解は通常の予測には使用・表示しない。

## 4. 再現可能な合成データ
6シナリオ：曜日差、月末集中、長期的な増減、途中の処理速度低下、突発的な件数増加、低負荷・休止。
非負の件数と所要時間を生成する。所要時間は起動コスト・件数・負荷時の非線形遅延・ノイズなどを含み、候補モデルの式そのものにはしない。
seed・開始日・観測日数を指定して再生成可能とする。観測180日、採点用未来30日、生成メタデータを別ファイルに保存する。
探索用seed 0〜4、最終用seed 100〜119。6×20=120の最終ケース。シナリオごとに乱数ストリームを分ける。
締切やデータ設定は最終採点結果を見て調整しない。予見困難なケース、未超過ケース、休止日を含める。

## 5. 予測手法
候補は3つに固定：
1. 比較基準：直近4回の同曜日の件数・所要時間平均。
2. 単純比較：直近7日の件数・所要時間平均。
3. カレンダー付きリッジ回帰：件数を曜日・月内日付・既知カレンダー特徴・過去ラグから予測し、観測済み件数と所要時間の関係から将来の所要時間を推定する。

候補3の特徴・学習窓・正則化・非負制約は最終採点前にコードと設定へ固定する。複雑な候補の追加を目的にしない。
1日先を順に予測する場合、未来の実件数ではなく予測値を再帰入力する。特徴の標準化は各foldの過去だけでfitする。
同じ観測・起点・予測日・締切で比較する。件数、時間は非負に制約し、実績は変更しない。

## 6. 評価とリーク対策
標準180点：
- 開発1〜120日、起点60/67/74/81/88で直後7/30日を採点。
- 監査121〜180日、起点120/127/134/141/148。開発で選んだ手法を固定し、各起点までの観測だけで再学習。
- 最終は180点で再学習し、未使用の未来30日を一度予測。1/7/30日を集計。
- 選択は開発7日間の所要時間MAE。最良値×1.05＋0.1分以内なら同曜日平均、7日平均、リッジの順に単純さを優先。
- 150点未満は初版の正式対象外。150〜179点の起点は末尾60日監査を確保して縮小し、小標本と明記。

指標：件数MAE、時間MAE/RMSE、終点誤差、単純比較に対する改善率、締切超過の見逃し・誤警報・正検知・正否定、最終着手日時の誤差、ケース数、失敗数、学習・予測時間。
基準誤差0は改善率N/A。重なるfold・同ケース内の日を独立標本として信頼区間にしない。ケース単位とシナリオ別、全候補、悪いケースを残す。
設定・データ・予測コード・依存・seedのハッシュを最終採点前に保存。結果の上書きを防ぐ。採点後のチューニングは禁止。変更が必要なら旧結果を開発結果として保持し未使用seedで再評価する。

監査テスト：
- 未来の正解の改変・行追加で同一起点の予測・選択・fitパラメータが不変。
- 全foldで学習末日＜採点初日。
- 評価器から予測器へ正解や生成メタデータを渡さない。
- 再帰予測と標準化が未来実績を使わない。
- 同曜日・7日平均・日跨ぎ期限を手計算照合。
- 件数0・時間0・減少・欠損・重複・不正設定を検証。
- 予測と実績の比較表示が同じ日付で対応する。
- 最新予測では未来の真の件数を使えないことをインターフェースで制約。

1. 本仕様を作成し、Claude Opusで設計と業務上の解釈をレビュー。
2. 生成器・入力検証・比較基準・期限計算を実装し、監査テストを実行。
3. リッジ候補と評価器、凍結・全件記録を実装。探索データだけで動作を確認。
4. API・業務UI・サマリ・予測対実績比較を接続。実装作業には必要に応じて実装向けモデルを使用。
5. Claude Sonnetでコードの独立レビュー。重大な評価上の懸念はOpusへ再確認。
6. 設定を凍結し、最終評価を一度実行。成績が悪くても変更せず報告。
7. 実ブラウザで全フロー・PC/スマホ・保存を検証。README・評価・監査・デモ台本・スクリーンショットを保存。

## 8. 完成条件
起動できるアプリ、日次180点のデモ、全候補の評価結果、監査テスト、サマリ出力、実績比較、説明文書が揃うこと。実行した検証だけを完了として記録する。
「実務需要が検証済み」「実データ精度が保証される」「リークや過学習が完全にない」とは表現しない。

## 9. 実装前の確定事項（設計レビュー反映）
- 選択はケース単位。正則化α=10、学習窓=直近120日、ラグ特徴の準備期間28日。採点結果による探索は行わない。
- 月内特徴はsin/cos、月初3日、月末3日、曜日、日付トレンド。所要時間も過去ラグを持ち、将来は予測件数・予測所要時間のみを再帰入力する。
- 基準改善率=100×(weekday4のMAE−対象MAE)/weekday4のMAE。基準0ならN/A。0件の日も単純平均から除外しない。
- 観測N点で開発末尾=N−60。開発起点はmax(60,N−120)から7刻みでN−90以下の最初5点。監査起点はN−60から7刻み5点。150点では開発1起点であることを表示。
- 業務日Dに開始。締切時刻が開始以下ならD+1日、それ以外はD日。等しい時刻なら24時間後。
- 完了=開始+予測所要時間、余裕=締切−完了。余裕<0は超過、0以上安全余裕未満は不足、その他は余裕あり。
- 計画の所要時間は秒に切り上げる。誤差MAE/RMSEは分の元数値。終点誤差はhorizon最終日の予測所要時間−実績所要時間、絶対値も記録。完了時刻誤差は秒切上げ後の予測完了−実績完了。最終着手誤差はその符号反転。
- 画面の代表最終着手日時は、余裕が最小の日の値（同率は先の日）。各日の値は表に併記。
- 実件数>0の日のMAE・締切混同行列も最終評価に出力する。全0の場合はactive MAEをN/A。
- 入力上限は1日10億件、10080分（7日）。極端値の誤入力を検出する初版の対応範囲。連続実行の重なり・待ち行列を考慮しない。
- 開発・監査結果を見てモデル設定を変えない。改修時は旧結果を保存し、未使用seedで新プロトコルとして評価する。
- 予測も10億件・10080分を対応上限とし、超過時は上限へ丸めず明示エラー・評価失敗として記録する。
- 合成seedを独立にしても同じ生成器由来の偏りは残る。実データ検証の代替ではない。
